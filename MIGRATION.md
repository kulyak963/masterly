# Переезд на российскую инфраструктуру

Составлено 2026-09-08. Две независимые причины, обе требуют одних и тех
же работ, поэтому делаются одним заходом.

| Причина | Что требует |
|---|---|
| **152-ФЗ, ст. 18 ч. 5** | база с персональными данными граждан РФ должна находиться в России |
| **406-ФЗ, с 01.12.2023** | нельзя авторизовать граждан РФ через иностранные сервисы (Google, Apple и др.) |

Не юридическая консультация. Формулировки требуют проверки юристом —
особенно спорный вопрос в конце документа.

## Почему именно сейчас

Выгрузка на 2026-09-08 (`node scripts/export-all.mjs`):

```
Каталог (обезличенный):     universities 131,  programs 1492
Персональные данные:        profiles 2,  favorites 8,  payment_events 1
Пользователи:               2  (1 email, 1 google — запрещён)
```

**Весь персональный слой — 11 строк и 2 аккаунта.** На этом объёме
перенос занимает вечер. На тысяче пользователей это уже проект с
планируемым простоем, переносом паролей и риском потерять данные.
Стоимость переезда растёт с числом пользователей и больше никогда не
будет такой низкой.

Каталог (1623 строки) персональных данных не содержит и по закону
переезжать не обязан — но держать две базы солобизнесу дороже, чем одну,
поэтому переносим всё.

## Что понадобится от Дениса

1. **Российское облако** — Yandex Cloud, VK Cloud, Selectel, Timeweb.
   Нужна виртуальная машина под свой Supabase (2 vCPU / 4 ГБ достаточно
   с большим запасом на текущий объём).
2. **Аккаунт разработчика Яндекс ID или VK ID** — чтобы получить
   `client_id` и `client_secret` для входа взамен Google.
3. **СМС-провайдер** (SMS.ru, SMSC или аналог) — если делаем вход по
   телефону.
4. **Уведомление в Роскомнадзор** — подаётся бесплатно и не зависит от
   техники. Отсутствие уведомления — самостоятельный штраф 100–300 тыс ₽
   за сам факт обработки данных, даже без утечки. Это самое дешёвое
   действие с самым большим эффектом, делать первым.

## Порядок работ

### Шаг 1. Резервная копия

```bash
node scripts/export-all.mjs
```

Пишет в `backup/<дата>/`. Папка в `.gitignore` — там имена, почты и
анкеты живых людей, коммитить нельзя.

### Шаг 2. Поднять свой Supabase на российском сервере

Используем **официальную сборку** Supabase для самостоятельного размещения, а не
самописную конфигурацию: она поддерживается, обновляется и не содержит
наших ошибок. Инструкция — в документации Supabase, раздел Self-Hosting
(docker compose).

После установки записать себе:
- адрес API (`https://<домен-или-ip>`),
- ключ `anon`,
- ключ `service_role`.

Обязательно: HTTPS, закрытый порт Postgres наружу, автоматические
резервные копии на стороне облака.

### Шаг 3. Перенести данные

```bash
TARGET_SUPABASE_URL=https://<новый-адрес> \
TARGET_SUPABASE_SERVICE_ROLE_KEY=<service_role нового сервера> \
node scripts/import-all.mjs backup/<дата>
```

Без `--apply` — только проверка. Скрипт отказывается писать, если цель
совпадает с текущей боевой базой.

Схему таблиц (`sql/*.sql`) нужно применить на новом сервере **до**
загрузки данных — порядок тот же, в котором файлы создавались.

**Про пароли.** Хеши паролей лежат в служебной таблице и через
клиентскую библиотеку недоступны. При двух аккаунтах проще не переносить
их вовсе: скрипт создаёт пользователей заново без пароля, человек задаёт
его сам. Идентификаторы при этом меняются — если в `profiles`/`favorites`
останутся ссылки на старые `user_id`, их надо перепривязать по адресу
почты (при двух аккаунтах — руками).

### Шаг 4. Переключить приложение

В `.env.local` и в переменных Vercel заменить:

```
NEXT_PUBLIC_SUPABASE_URL       → адрес нового сервера
NEXT_PUBLIC_SUPABASE_ANON_KEY  → anon нового сервера
SUPABASE_SERVICE_ROLE_KEY      → service_role нового сервера
```

Код менять не нужно: клиент везде берётся из `lib/supabase.ts` и
`lib/supabaseAdmin.ts`, оба читают эти переменные.

### Шаг 5. Заменить авторизацию (406-ФЗ)

Сейчас в коде четыре способа входа, и все завязаны на почту или Google:

| Где | Что |
|---|---|
| `app/login/page.tsx` | Google, ссылка на почту, пароль, код из письма |
| `app/page.tsx` (шаг 8) | Google, ссылка на почту, пароль, код из письма |

Что делать:

1. **Сначала добавить российский способ входа**, только потом убирать
   Google. Иначе аккаунт `kulyak963@gmail.com` — единственный владелец —
   потеряет доступ.
2. **Яндекс ID или VK ID.** Оба работают по OAuth 2.0. Переносимый
   способ, не зависящий от версии Supabase: провести обмен кодом в своём
   маршруте `app/api/auth/<провайдер>/`, а затем выдать сессию через
   админский `generateLink` и редирект. Это работает и на своём сервере,
   и на облачном.
3. **Вход по телефону** — самый бесспорный с точки зрения закона.
   Требует СМС-провайдера.
4. **Убрать Google** — две кнопки плюс упоминание в `app/terms/page.tsx`.

### Шаг 6. Обновить документы

- `app/privacy/page.tsx` — заменить врезку «требованию не соответствуем»
  на описание нового положения дел.
- `app/terms/page.tsx` — убрать «вход через Google», описать новые способы.
- Заполнить `lib/legal.ts` (реквизиты, `filled: true`).

## Открытый вопрос к юристу

Запрет 406-ФЗ на иностранные сервисы авторизации трактуется юристами
шире, чем «убрать кнопку Google»: встречается позиция, что **любой
иностранный адрес почты как идентификатор** (gmail, yahoo, outlook) —
включая вход по ссылке на такую почту — также не допускается.

От ответа зависит объём работ:

- если запрет только на OAuth — убираем Google, вход по почте остаётся;
- если запрет шире — вход по почте убирается совсем, остаются телефон и
  российские сервисы авторизации, и это заметно больше работы и заметно
  выше барьер для пользователя.

Также стоит уточнить действующий размер санкций: источники расходятся
(ст. 13.55 КоАП называет 10–50 тыс ₽, юридические обзоры — до 1,4 млн ₽
для юрлиц со ссылкой на новые поправки).
