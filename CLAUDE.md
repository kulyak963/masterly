## Бизнес-модель (решено 2026-08-25, пока не реализовано в коде)

Разбирали с Денисом какую модель монетизации выбрать. Итоговое решение —
**фиксировать здесь**, чтобы не забыть логику при реализации платежей.

**Не подписка помесячно.** Студент проходит поступление один раз за
6-12 месяцев, потом сервис ему не нужен — рекуррентные платежи = гарантированный
отток и злость. Плюс рекуррентные списания с российских карт на западных
платёжных системах — источник проблем сильнее разовых платежей.

**Не цена агентства (агентства берут от €1000) на текущий продукт.** Агентство
продаёт часы живого человека (проверяет дедлайны, правит SoP, отвечает за
результат). Mastersly сейчас — самообслуживание без человека в процессе;
часть данных — непроверенные оценки ИИ (см. раздел «Честность данных» выше).
Поставить цену агентства на продукт с таким уровнем доверия — тот же обман,
что мы весь день вычищали из интерфейса, только в прайсинге.

**Решение — лестница из тарифов, не одна цена:**
1. **Бесплатно навсегда** — воронка: весь опрос, оценка готовности, список
   программ, роадмап в общем виде, 1 программа в избранном.
2. **Self-serve Pro, разово ~1500-2000₽** (не в месяц) — полный доступ:
   неограниченное избранное/сравнение, полный Timeline/Gantt с экспортом,
   персональный ИИ-анализ программы. ИИ-фичи логично идут именно сюда — это
   единственное, что стоит денег в переменных расходах.
3. **Премиум/сопровождение, €300-600** — вот тут можно конкурировать с
   агентствами по цене, но только когда за тарифом стоит **реальный человек**
   (сначала Денис, потом можно нанять консультанта): личная проверка вузов
   из шортлиста студента, правка мотивационного письма, созвон. Дешевле
   классического агентства, потому что рутину уже сделал инструмент.

**Как поднять потолок цены тарифа 2 без человека в процессе** (обсуждали
отдельно, приоритет по эффекту):
- **Главный рычаг — реально проверенные данные** (см. `verified` колонку
  выше). Без этого любые новые фичи не поднимают воспринимаемую ценность —
  продукт всё ещё «симпатичный чек-лист с оговоркой не доверять датам».
- Трекинг статуса заявок (подал / собеседование / оффер / отказ) — продлевает
  использование на весь цикл, не только на этап планирования.
- Генератор документов (Academic CV с автоподстановкой, чек-лист перевода
  под конкретную страну) — деливерабл ощущается ценнее, чем просто совет.
- Сбор исходов от пользователей («получил оффер?» после дедлайнов) — со
  временем даёт свою статистику (у похожих профилей был шанс X%), которую
  никто не может скопировать — это ров (moat), не фича. Медленный эффект,
  стратегически самый ценный.
- Гарантия возврата денег при нуле офферов — чисто решение, без кода,
  снижает воспринимаемый риск покупки сильнее, чем скидка.

**Оплаты и флаг free/pro в профиле — ещё не реализованы.** Трекинг статуса
заявок — реализован на фронтенде 2026-08-27 (см. раздел «Трекер статуса
заявок» ниже), схема БД ждёт ручного запуска SQL. Следующий шаг по
монетизации — разметить границу free/pro в схеме (без реальной оплаты).

## Общий файл дизайн-токенов (редизайн 2026-08-27)

**До этой правки не было ни одного общего файла с цветами/шрифтами** — каждая
страница (11+ файлов) объявляла свои копии `bg0/t1/t2/t3/gold/sans/serif/mono`
и т.д. Копии успели разъехаться: у `app/page.tsx` золотой был `#D4A853`, у
всех остальных страниц — `#C8A256`; у privacy/terms был свой серый. Теперь:

- **`lib/theme.ts`** — единственный источник цветов/шрифтов/шкалы отступов
  (`space`)/скруглений (`radius`)/теней (`shadow`). Канонический золотой —
  `#C8A256` (то значение, что уже было в большинстве файлов).
- **`components/PhotoCycler.tsx`** — общий слайдшоу-компонент фото городов
  (+ `CITY_SHOTS`/`CITY_LARGE` списки), раньше был продублирован в
  `app/page.tsx` и `app/login/page.tsx`.
- **`components/VerifiedBadge.tsx`** — общий бейдж «✓ проверено / ⚠ оценка
  ИИ», раньше был продублирован в `app/dashboard/page.tsx` и инлайн в
  `app/program/[id]/page.tsx`.

**Правило на будущее**: новый код с цветами/шрифтами должен импортировать из
`@/lib/theme`, а не объявлять свои `const bg0 = '#0A0A0C'` заново — это и
есть причина, по которой цвета разъехались в прошлый раз.

Заодно в этом же проходе почищены: наведение мышью на строки списков
избранного/канбана заявок в личном кабинете (раньше `.hc` не давал вообще
никакой обратной связи), адаптивность сетки выбора стран на шаге 5 анкеты
под мобильный экран, и жёстко выключенный зум страницы (`userScalable:false`
в `app/layout.tsx`) — доступность.

**Важные уроки по картинкам (не наступать снова):**

## Бэкенд-архитектура (2026-08-24)

**Важно: прокси `api.vibecode-claude.online` — это НЕ баг и не костыль.** Это
единственный сейчас способ платить за доступ к Claude из России (нет карты для
официального `api.anthropic.com`). Любые будущие изменения не должны исходить
из «просто переключить на официальный API» — база URL и модель нарочно вынесены
в конфиг, чтобы провайдера можно было сменить без правки кода, но по умолчанию
всегда прокси.

### Общий AI-клиент — `lib/ai.ts`
Единая точка входа для всех вызовов Claude: `askAI(prompt, opts)` +
`extractJson(text)`. Конфигурируется из `ANTHROPIC_API_KEY` / `ANTHROPIC_BASE_URL`
/ `ANTHROPIC_MODEL` — нигде в коде эти значения не хардкодятся. Любой новый
AI-фичер (например, будущий SoP-ассистент) должен переиспользовать эти же две
функции, а не заводить свой `new Anthropic(...)`.

`app/api/verdict/route.ts` использует этот клиент и оборачивает вызов в
try/catch — при ошибке (например, `insufficient_credits`) возвращает чистый
JSON `{error}` с кодом 502 вместо пустого 500.

Подтверждено прямым тестом: прокси принимает имя модели `claude-sonnet-4.6`
(ошибка была именно про баланс — `403 insufficient_credits` — а не про
неизвестную модель). Баланс на аккаунте прокси нужно пополнить, чтобы кнопка
«Персональный анализ» в дашборде и наполнение базы вузов заработали.

### Service-role доступ — `lib/supabaseAdmin.ts`
Второй Supabase-клиент, отдельный от `lib/supabase.ts` (anon key). Использует
`SUPABASE_SERVICE_ROLE_KEY` (секрет из Supabase Dashboard → Settings → API →
`service_role`) и нужен только для серверных операций записи, которые не
разрешены анонимному ключу по текущим RLS-политикам (`universities`/`programs`
дают анону только `SELECT`). Инициализация ленивая (`getSupabaseAdmin()`) —
специально, чтобы отсутствие ключа не ломало сборку, только конкретный запрос.
**Никогда не импортировать этот клиент в клиентские компоненты.**

### Автонаполнение базы — `app/api/admin/seed-programs/route.ts`
Заменяет `app/dashboard/fill_db.py` (логика 1:1 перенесена на TypeScript, тот
же перебор 20 стран × 8 направлений с проверкой на дубли). Отличия:
- Требует заголовок `Authorization: Bearer $CRON_SECRET` — так Vercel Cron
  сам подписывает запросы, когда задан `CRON_SECRET`, без кастомной схемы.
- `?country=de&field=Computer%20Science` — ручной прогон одной комбинации
  (для теста через curl/браузер с секретом).
- Без параметров — весь список сразу, но с бюджетом по времени (`maxDuration=60`,
  внутренний cutoff 50с) — обрабатывает сколько успевает и возвращает
  `stoppedEarly: true`, если не уложился. Раз уже обработанные комбинации
  пропускаются мгновенно (дедуп-проверка), после первого полного прогона
  еженедельный cron будет обрабатывать только новые страны/направления и
  укладываться быстро.
- Расписание — `vercel.json` в корне, по умолчанию понедельник 03:00 UTC.

**`fill_db.py` пока НЕ удалён** — по плану он удаляется только после того, как
новый роут подтверждённо отработает end-to-end (нужны реальный
`SUPABASE_SERVICE_ROLE_KEY` и баланс на прокси, которых пока нет). Не удалять
раньше, чем реально протестирован.

### Заложено на будущее, но не реализовано
Паттерн общий для всех — используем `askAI`/`extractJson` из `lib/ai.ts`, ничего
нового изобретать не нужно:
- **SoP-ассистент**: `app/api/sop-draft/route.ts`, по образцу `verdict/route.ts`.
- **PDF-экспорт шортлиста**: чисто клиентский код (например `@react-pdf/renderer`),
  бэкенд не нужен.
- **Аналитика (Posthog)**: клиентский скрипт + `NEXT_PUBLIC_POSTHOG_KEY`,
  без кастомного бэкенда.
- **SEO-страницы программ** (`app/program/[id]/page.tsx`): серverкомпонент,
  читает напрямую через `lib/supabase.ts`, статика/ISR — новый бэкенд не нужен.

## Честность данных (2026-08-24)

Прямая проверка живой базы (281 программа, 117 вузов) нашла реальный баг:
у ~30 программ (`field = 'Computer Science / AI'` или `'Engineering'`) значение
не совпадает ни с одним значением, по которому фронтенд фильтрует программы —
эти строки никогда не показывались ни одному студенту. SQL-фикс подготовлен и
передан Денису для самостоятельного запуска в Supabase SQL Editor (там же
добавляется колонка `programs.verified boolean` + `verified_at`).

**Колонка `verified`**: `false`/`null` по умолчанию — значит данные программы
сгенерированы ИИ и не проверены человеком. `true` — проверено вручную против
официального сайта вуза. UI показывает бейдж `VerifiedBadge` (в
`dashboard/page.tsx`) везде, где отображается программа: список, модалка,
таблица сравнения.

**GanttTimeline.tsx / Timeline.tsx** теперь принимают проп `programs` (реальные
избранные/подобранные программы с `deadline_month`/`deadline_day`/`url` из БД)
вместо старых захардкоженных «одна дата на страну» словарей. Если когда-нибудь
понадобится что-то похожее — **никогда не хардкодить даты в компоненте**,
всегда брать из переданных программ.

**Timeline.tsx экспортируется, но нигде не рендерится** в `dashboard/page.tsx`
(на вкладке «Таймлайн» используется только `GanttTimeline`) — обнаружено при
этой правке, похоже на мёртвый код или недоделанный свитч между двумя
вариантами таймлайна. Не трогал, просто фиксирую факт.

## Авторизация (2026-08-24, вторая правка)

Было 3 реальные проблемы, все нашёл и починил:

1. **`app/page.tsx` никогда не проверял сессию** — залогиненный пользователь,

## Код из письма как альтернатива ссылке (2026-08-27)

**Проблема, которую не решает автовход выше**: тот механизм (стучаться
`signInWithPassword` каждые 4с) работает только когда задан пароль. Вход
**по ссылке без пароля** (`sendMagicLink`/`loginWithEmail`, ветка
`else { signInWithOtp(...) }`) технически не может так работать — magic-ссылка
привязывается к тому браузеру, где её открыли, и подтверждение на телефоне
никак не сообщает об этом компьютеру (нет общего секрета, который можно
подставить). Это не баг, это то, как устроен вход по ссылке в принципе.

**Решение**: на экране «Проверь почту» (и в `app/page.tsx`, и в
`app/login/page.tsx`) добавлено поле для 6-значного кода из того же письма —
`supabase.auth.verifyOtp({email, token, type:'email'})`. Код можно прочитать
на телефоне и ввести на компьютере вручную, в той же вкладке, где начинали.

**Важно — без этого код просто не придёт**: Supabase Dashboard →
Authentication → Email Templates → Magic Link — в тексте письма должна
присутствовать переменная `{{ .Token }}` (по умолчанию Supabase иногда кладёт
в шаблон только `{{ .ConfirmationURL }}`, без кода). Денису нужно один раз
проверить/добавить `{{ .Token }}` в шаблон письма — это настройка в панели,
не код, я не могу сделать это из репозитория.

## Автовход после подтверждения email (2026-08-24, четвёртая правка)

**Нашёл и починил настоящий баг с бесконечной перезагрузкой**, который сам же
создал правкой №2. Причина: `app/page.tsx` редиректит на `/dashboard`, если
есть сессия; `dashboard/page.tsx` редиректил на `/`, если анкета не найдена.
Если сессия есть, а анкеты нет (например, письмо подтвердили на телефоне, где
`localStorage` пустой) — получался бесконечный пинг-понг `/` ↔ `/dashboard`.

Фикс: `dashboard/page.tsx` **больше не делает автоматический редирект** на
`/`, если анкета не нашлась — вместо этого показывает экран с ручной кнопкой
«Пройти опрос заново» и «Выйти». Автоматический редирект — единственное, что
может зациклиться; ручной клик — нет. **Правило на будущее: между двумя
страницами нельзя ставить взаимные условные редиректы одновременно — либо
редиректит только одна сторона, либо решение принимает пользователь руками.**

**Плюс сделали то, что реально просил Денис**: подтверждаешь email хоть с
телефона — вход происходит на **компьютере**, где начал регистрацию, а не на
устройстве, где кликнул по ссылке. Механизм: пока показан экран «Подтверди
почту» (и в `app/page.tsx`, и в `app/login/page.tsx`), открытая вкладка каждые
4 секунды тихо пробует `signInWithPassword` с уже известными на этом
устройстве email+паролем. Пока почта не подтверждена — Supabase просто
отклоняет попытку, ошибка не показывается. Как только подтверждение прошло
(с любого устройства) — попытка на компьютере проходит и он сам заходит в
дашборд. `pending_profiles` (см. выше) при этом не обязателен для этого
сценария — анкета на компьютере и так лежит в его `localStorage`, это тот же
браузер, что заполнял опрос.

## Фикс: обновление страницы сбрасывало ожидание подтверждения email (2026-08-27)

Денис нашёл реальный баг руками: если на экране «Подтверди почту» (после
регистрации с паролем) обновить страницу — человека выкидывало в начало
анкеты (`step` возвращался к 0), а автовход выше переставал работать вообще,
потому что зависел от него.

**Причина**: `signupPending`, `password` и (в `app/page.tsx`) `step` — обычный
`useState`, ничем не сохранённый. Обновление страницы = новый рендер с нуля.
Опрос (`a`) кладётся в `localStorage` только на переходе step 7→99, а вот сам
факт «жду подтверждения» и пароль нигде не переживали F5.

**Фикс** (в `app/page.tsx` и `app/login/page.tsx` одинаково): при входе в
режим ожидания — `sessionStorage.setItem('masterly_pending_signup', {email,
password})`. При старте компонента (там же, где уже был `getSession()`) —
если сессии нет, но эта запись в `sessionStorage` есть, восстанавливаем
`signupPending`/`password`/email и (в `app/page.tsx`) `step=8`, чтобы отрисовался
именно экран «Подтверди почту», а не начало опроса. Запись чистится при
успешном автовходе и при ручном «Назад».

Специально `sessionStorage`, не `localStorage` — переживает F5 в этой же
вкладке, но не остаётся в браузере навсегда (пароль в открытом виде, пусть и
свой собственный, не должен лежать на диске дольше, чем нужно).

## Трекер статуса заявок (2026-08-27)

Первая фича из лестницы монетизации (см. «Бизнес-модель» выше) — статус
заявки по каждой избранной программе: не подано / подано / собеседование /
оффер / отказ. Статус хранится прямо в таблице `favorites` (не отдельной
таблицей) — она уже хранит `user_id`+`program_id` по каждой избранной
программе, отдельная сущность не нужна.

**Фронтенд готов** (`app/dashboard/page.tsx`): состояние `favorites` стало
`Map<program_id, {status, status_updated_at}>` вместо `Set<program_id>` —
методы `.has()`/`.size`/`.delete()` у Map те же самые, что и у Set, так что
почти весь старый код с фильтрацией избранного не тронут. Выпадающий список
статуса — во вкладке «Избранное», прямо на строке карточки программы, между
оценкой и кнопкой ♥. Функция `updateApplicationStatus()` обновляет и
локальное состояние, и строку в Supabase.

**Схема БД ещё НЕ применена — нужно запустить в Supabase SQL Editor:**

```sql
alter table favorites
  add column if not exists status text not null default 'not_applied'
    check (status in ('not_applied','applied','interview','offer','rejected')),
  add column if not exists status_updated_at timestamptz not null default now();

drop policy if exists "favorites_update_own" on favorites;
create policy "favorites_update_own"
  on favorites for update
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);
```

До этого запроса фронтенд будет пытаться читать/писать несуществующие
колонки `status`/`status_updated_at` — `select`/`update` будут падать молча
(Supabase просто не найдёт колонку), сам список избранного при этом не
сломается, потому что старые поля (`program_id`) как читались, так и читаются.

**Не проверено вживую** — вкладка «Избранное» требует реального логина
(Google/email), через который агент проходить не должен (см. пункт 3 в
«Известные проблемы» выше — та же причина). Проверено только `npx tsc
--noEmit` и `npm run build` — оба проходят чисто. Денису стоит один раз
глазами свериться после того, как SQL выше применён.

**Дальше по этой ветке (не сделано)**: статусы «принял/отклонил оффер», сбор
агрегированной статистики по исходам (см. «Бизнес-модель» — это ров, самый
ценный, но медленный эффект).
